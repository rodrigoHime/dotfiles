A normal day

The shape of a session, start to finish — everything below is covered in its own section further down.

Open iTerm2.

Launches into the "dotfiles" profile (Meslo Nerd Font, the "peru" oh-my-posh prompt).

Attach or start a tmux session.

tmux for a new one, tmux a to reattach — continuum auto-saves and restores your panes, so a reboot doesn't lose your layout.

Split panes for the tools you're running.

One for nvim, one for a dev server or test watcher, one for cc (Claude Code) — Ctrlh/j/k/l moves between them, and between nvim splits, without thinking about which one you're in.

Open the project in nvim.

nvim . from the project root; the Explorer sidebar opens by itself next to the dashboard. Use it or the file picker to get around, LSP for navigation and diagnostics, Diffview/LazyGit for review.

Edit → check the diff → commit.

<leader>gd to see everything you've changed before you stage it, <leader>gg to commit from LazyGit without leaving nvim.

Terminal: iTerm2 + tmux

iTerm2 is the window; tmux is what actually manages sessions, windows and panes inside it — and what survives a reboot.

tmux essentials

Prefix is Ctrla (not the tmux default Ctrlb) — press it, release, then the key below.

KeysDoes
prefix |Split side by side (new pane on the right), opens in the current pane's directory
prefix -Split top/bottom, same directory
prefix cNew window, same directory
Ctrl h/j/k/lMove between panes — and seamlessly into/out of nvim splits, no prefix needed
prefix H/J/K/LResize the current pane (repeatable — hold)
prefix zZoom the current pane to fill the window; press again to restore
prefix x / dClose the pane / detach from the session
prefix :tmux command prompt — split-window -h works whatever your keyboard does with |
prefix rRe-source the tmux config (does not restart the server)
mouseClick to select a pane, drag borders to resize, scroll to scroll back — mouse mode is on
Changed a tmux setting? tmux reads its config once, when the server starts. After a switch, run tmux kill-server from outside tmux and open a fresh session — otherwise the running server keeps the old bindings.
Your layout survives a reboot. resurrect + continuum auto-save your session every 15 minutes and restore it the next time tmux starts — tmux a after restarting your Mac should put you back where you left off, panes included.

iTerm2

The "dotfiles" profile is declared in home/iterm2.nix — Meslo Nerd Font (needed for the prompt's glyphs and nvim's icons), unlimited-feeling scrollback, no bell noise. Two things live at the macOS app-preferences level and need a one-time click each — see Manual steps below.

Shell: zsh + oh-my-posh

oh-my-zsh supplies the framework (git/macos/colored-man-pages/command-not-found plugins, autosuggestions, syntax highlighting); oh-my-posh owns the prompt itself, rendering your "peru" theme.

Keys / commandDoes

Ctrl tfzf: fuzzy-find files, insert the path at the cursor

Neovim basics

Everything from here down is nvim (LazyVim base). One habit makes the rest of this page mostly unnecessary to memorize:

Press Space and wait. That's the leader key — every keymap below starts with it. Pausing after it pops up which-key: every available next key, grouped and labelled, live. You genuinely don't need to memorize most of this page — you need to know it exists, then let which-key remind you. <leader>? shows the full list for the current buffer at once.

Navigate & find

Three complementary ways to get to a file or a symbol — Explorer when you want to see the tree, Picker when you know roughly what you're looking for, Harpoon for the handful of files you're living in right now.

File tree

Explorer

A persistent sidebar tree of the project, git-status glyphs on every changed file. snacks.nvim, part of LazyVim's core.

Try it: <leader>e opens it rooted at the project; <leader>E roots it at your current directory instead. Inside: Enter opens, a creates, d deletes, r renames. Also opens automatically whenever you launch nvim <a-directory> (e.g. nvim .) - the dashboard still shows too, this just saves the <leader>e press. Plain nvim with no argument is unaffected.

Fuzzy finder

Picker

Type a few letters of a filename or a grep term, jump straight there. Also snacks.nvim.

Try it: <leader><space> find files, <leader>/ live grep across the project, <leader>, switch buffers, <leader>fr recently opened files.

Quick bookmarks

Harpoon2

For the 3–5 files you're actually editing right now — faster than re-searching for the same file for the tenth time today.

Try it: <leader>H to pin the current file, <leader>h to see/manage your pinned list, then <leader>1-<leader>9 to jump straight to any of them from anywhere.

Structure

Outline & breadcrumbs

A sidebar listing every function/class/method in the current file, plus a winbar showing exactly where the cursor sits in that structure.

Try it: <leader>cs toggles the outline sidebar, click any entry to jump. The breadcrumb (module > class > function) just shows up above the buffer automatically — nothing to press.

Git & code review

Four tools, each for a different moment — a quick glance at a hunk, reviewing everything you've changed, staging/committing, or working with GitHub itself.

Inline

gitsigns

A +/~/- column in the gutter next to every changed line, always on, no toggle needed.

Try it: <leader>gb blames the current line; hover a changed line for a hunk preview.

Review everything

Diffview

The main event for "what did I actually change" — a changed-files tree on one side, the diff for whichever one you've selected on the other. Exactly VS Code's Source Control diff view.

Try it: <leader>gd opens it. <leader>gh shows the history of just the current file, <leader>gH the whole repo's history. <leader>gs is the lighter-weight version — a quick changed-files list with a diff preview, no separate panel.

Full client

LazyGit

The entire TUI git client in a floating window — stage hunks, commit, branch, stash, rebase, push — without leaving nvim or opening a new pane.

Try it: <leader>gg. q closes it. Space stages/unstages under the cursor, c commits.

GitHub

Octo

Browse and act on GitHub issues and PRs as regular nvim buffers — comment, review, change labels, all as text.

Try it: <leader>gi your open issues, <leader>gI search all issues, <leader>gp/<leader>gP the PR equivalents, <leader>gr list repos. Needs gh auth login once first — see Manual steps.

Everyday how-tos

Small things that come up constantly once you're actually working — each answered once, here.

Undo

Revert changes in a file

Press <leader>gh and wait — which-key shows the gitsigns hunks menu.

Try it: R = Reset Buffer (discard every unstaged change in the file), r = Reset Hunk (just the chunk under the cursor). In the same menu: s/S stage a hunk/the buffer, u undo a stage, p preview a hunk inline, b/B blame line/buffer, d Diff This, D the "Diff This ~" variant against an earlier revision.

Reset restores the index version, so anything you already staged stays. For a true "back to the last commit" revert, open LazyGit (<leader>gg), select the file and discard its changes there.

Diff

Close a diff view

"Diff This" opens a plain pair of splits, not the Diffview tab.

Try it: close either half (:q or Ctrlw q) and the other leaves diff mode by itself, or press Ctrlw o in the window you want to keep to close everything else. The Diffview panel (<leader>gd) closes with :DiffviewClose.

Keys

<leader>gh is two things

This repo binds <leader>gh to Diffview's "current file history"; LazyVim core uses the same prefix for the hunks menu (<leader>ghs, <leader>ghr…). In practice which-key shows the hunks menu. If Diffview's file history ever seems unreachable, that's why — <leader>gH (repo history) is unaffected.

Projects

Start on a project, or switch projects

nvim . (or nvim <folder>) opens the Explorer next to the dashboard automatically.

Try it: on the dashboard, p opens the Projects picker (folders you've opened before); from inside nvim it's <leader>fp. A brand-new folder just needs cd + nvim . once.

tmux

Panes

prefix | splits side by side, prefix - top/bottom, both in the current directory. prefix z zooms the current pane to fill the window (and restores it); prefix x closes it; prefix d detaches. The prefix is Ctrla, not tmux's default Ctrlb.

nvim

The swap-file prompt

"Found a swap file … already exists!" means a previous nvim on that file never exited cleanly (closed tab, sleep, killed pane). Compare the dates in the prompt.

Try it: if the swap is far newer than the file's last save and you weren't mid-edit, press D to delete it. Press R first to recover and inspect it if you might have lost work, O to open read-only. Avoid E unless you're sure no other nvim has the file. Swap files live in ~/.local/state/nvim/swap/.

Write & refactor

Formatting and linting already run automatically (Mason installs the right tool per language the first time you open a matching file) — these are the tools for actively reshaping code.

<leader>rxExtract the selected code into a new variable
<leader>rfExtract the selection into a new function
<leader>riInline a variable at the cursor back into its uses

Debug & test

Both are opt-in per project: debugging needs a debug adapter that matches the language (Ruby and JS/TS already have theirs wired up), testing needs neotest to recognize your test framework's config file.

Breakpoints

Debugging (nvim-dap)

Ruby gets a debug adapter automatically (needs the debug gem in that project's Gemfile); JS/TS gets one too (js-debug-adapter, installs itself via Mason the first time you debug).

A typical session: <leader>db on the line you want to stop at, <leader>dc to run until you hit it, then <leader>di/<leader>dO/<leader>do to step into/over/out, <leader>du to see the full debugger UI (variables, call stack, watches), <leader>dt to stop.

Test runner

Testing (neotest)

Ruby uses RSpec automatically. JS/TS supports both Jest and Vitest — whichever config file your project has is the one that activates.

Try it: <leader>tr runs the nearest test to the cursor, <leader>tt the whole file, <leader>tT every test file in the project. <leader>ts toggles a summary panel (pass/fail per test), <leader>to shows a failure's output, <leader>td runs the nearest test under the debugger instead.

Tasks & REST

Task runner

Overseer

Run and watch build/test/lint/dev-server commands from inside nvim instead of a separate terminal pane — closer to VS Code's tasks.json than a raw shell.

Try it: <leader>oo run a task, <leader>ow see the task list/output, <leader>ot act on a running task (restart, stop, open its terminal).

HTTP client

REST client (kulala.nvim)

Write a request as plain text in a .http file, run it, see the response inline — a lightweight Postman for quick API checks.

Try it: open or create a .http file, put the cursor inside a request block, <leader>Rs to send it. <leader>Rr replays the last request.

Changing the config

Nvim's config lives in home/nvim/lua/ in the repo — editing it there is editing your live config, no deploy step.

I want to…Do this
Enable another LazyVim language/feature extraAdd { import = "lazyvim.plugins.extras.<path>" } to home/nvim/lua/config/lazy.lua's spec table, then switch + relaunch nvim
Add a plugin LazyVim doesn't ship as an extraNew file under home/nvim/lua/plugins/ returning a plugin spec table (see plugins/git.lua or plugins/testing.lua for the pattern)
Change a keymaphome/nvim/lua/config/keymaps.lua for a global one, or next to the plugin spec that owns it
Apply the changeswitch, then quit and relaunch nvim so lazy.nvim picks up the new spec
Lock in new plugin versions after thatlazy-lock.json updates itself on launch (it's an out-of-store symlink into the repo) — just git add -A && git commit once you're happy

How it fits together

The Nix side in plain terms — enough to know where to edit and why a rebuild behaves the way it does.

Nix

Flake

flake.nix is the repo's entry point. Its inputs are the pinned dependencies (nixpkgs, nix-darwin, home-manager); its outputs are the two machine configurations, rodrigos-macbook-pro and rodrigos-work-macbook. flake.lock records the exact commit of every input, which is why both Macs build identical versions until you run nix flake update — the same idea as lazy-lock.json for nvim plugins.

Two consequences: evaluation is pure (a flake can't read $USER or other environment at build time — hence the work username written into flake.nix, which bootstrap.sh fills in for you), and a flake only sees files git tracks — git add a new file before a rebuild.

Nix

home-manager

nix-darwin manages the machine (macOS defaults, Homebrew casks); home-manager manages everything under your home directory — shell, tmux, git, the nvim config, user CLI tools. Here it runs as a nix-darwin module, so one switch rebuilds both. home/home.nix imports zsh.nix, tmux.nix, iterm2.nix and nvim/nvim.nix.

Two ways to configure a tool: a programs.<tool> module (programs.tmux, programs.zsh, programs.git, programs.oh-my-posh) — typed options, home-manager generates the config file, so search its options list for programs.<tool> first; or plain files via home.file / xdg.configFile (used for nvim and the iTerm2 profile). lazy-lock.json uses mkOutOfStoreSymlink because lazy.nvim rewrites it and Nix store paths are read-only.

The generated files in ~ are symlinks into /nix/store, so editing them by hand does nothing durable: edit the .nix file, switch, restart whatever reads the config. Each switch is a generation — sudo darwin-rebuild --rollback returns to the previous one. Leave home.stateVersion alone; it isn't a version to upgrade.
